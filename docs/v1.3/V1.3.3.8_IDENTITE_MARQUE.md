# v1.3.3.8 — Identite de marque comprise par les moteurs

Troisieme passe SEO sur la vitrine publique. Les deux precedentes
(`v1.1.10.3` puis [`v1.1.12`](../v1.1/V1.1.12_SEO_BALISAGE.md)) ont rendu le
site indexable et lui ont donne un balisage schema.org complet. Celle-ci ne
corrige ni l'indexabilite ni la couverture du balisage : elle corrige **a qui
ce balisage attribue le site**.

Garde-fou : `npm run test:brand`
([`verify-brand-identity-contract.mjs`](../../apps/webportal/scripts/verify-brand-identity-contract.mjs)),
integre a `npm run validate`.

## Le defaut

`Zachary IT` est le nom commercial ; `Zachary HOUNSA-HOUNKPA EI` est la
denomination juridique. Le balisage declarait l'inverse de ce qu'il fallait :

| Noeud | Avant | Consequence |
|---|---|---|
| `WebSite.name` | `Zachary HOUNSA-HOUNKPA EI` | c'est ce champ que Google lit pour determiner le **nom du site** affiche en resultat. Le site s'annoncait donc sous sa raison sociale. |
| `LocalBusiness.name` | `Zachary HOUNSA-HOUNKPA EI` | `name` doit correspondre a l'enseigne reellement affichee sur le site — l'en-tete affiche `Zachary IT`. |
| `LocalBusiness.alternateName` | `Zachary IT` | la marque etait releguee en variante. |

Le reste de la chaine etait deja correct et n'a **pas** ete retouche :
`og:site_name`, le gabarit de titre, l'en-tete public et les canonical
portaient deja `Zachary IT`.

## Ce qui change

### 1. Une seule source pour les deux identites

[`lib/brand-identity.ts`](../../apps/webportal/lib/brand-identity.ts) expose
`BRAND_NAME` et `LEGAL_NAME`. Les deux noms etaient auparavant recopies dans
trois fichiers, libres de diverger.

Ce module est **volontairement sans import** : `test:brand` le charge tel
quel, sans la resolution d'alias `@/` de Next, et verifie donc les valeurs
reelles et non une chaine relue dans du source.

Les deux valeurs viennent des mentions legales publiees
(`SeedContent/mentions-legales.md`, section « Editeur du site »), qui font
foi : « **Zachary HOUNSA-HOUNKPA EI** / Nom commercial : **Zachary IT** ».

### 2. Balisage corrige

```jsonc
// WebSite
{ "@id": "…/#website", "name": "Zachary IT",
  "alternateName": ["Zachary HOUNSA-HOUNKPA EI"],
  "publisher": { "@id": "…/#business" } }

// LocalBusiness
{ "@id": "…/#business", "name": "Zachary IT",
  "legalName": "Zachary HOUNSA-HOUNKPA EI",
  "address": { "addressLocality": "Guichen", … },
  "areaServed": [{ "@type": "City", "name": "Guichen" }, …] }
```

`legalName` est la propriete schema.org prevue pour la raison sociale :
l'identite juridique n'est pas masquee, elle est rangee dans le bon champ.

La relation marque -> entite juridique -> Guichen -> domaine est portee par
ces deux noeuds et la **seule** relation `publisher`. Ne pas empiler
`founder`, `mainEntity`, `about` ou des `sameAs` supplementaires : un
`sameAs` mort ou une relation inventee degrade le balisage.

`LocalBusiness` est conserve. `ProfessionalService` reste proscrit pour la
raison deja documentee en v1.1.12 : schema.org l'a **deprecie** pour cause de
confusion avec `Service`.

Aucune donnee nouvelle : adresse, telephone et SIRET sont inchanges.

### 3. Titre de l'accueil

`Zachary IT | Sauvegarde informatique a Guichen (35)` — marque en tete,
localite conservee.

Piege verifie sur le HTML servi, contre-intuitif : le `title.template` du
layout racine (`%s | Zachary IT`) ne s'applique **qu'aux segments enfants**,
pas a `app/page.tsx`, qui partage le segment racine avec le layout
(cf. `resolve-metadata.js`, `if (i < metadataItems.length - 2)`). L'accueil
ecrit donc sa marque lui-meme. Toute autre page ne doit **jamais** suffixer
la marque, sous peine de `… | Zachary IT | Zachary IT` ; `test:brand`
l'interdit sur l'ensemble des `app/**/page.tsx`.

### 4. Pied de page public

Les deux noms se lisent ensemble, marque en tete. C'est le seul endroit
present sur toutes les pages publiques ou la relation est visible pour un
humain. L'en-tete de la coquille **authentifiee** (`AppShell`) n'est pas
touche : son usage est different.

### 5. Page `/a-propos`

Le contenu enonce desormais la relation : « Zachary IT est le nom commercial
de Zachary HOUNSA-HOUNKPA EI, micro-entreprise … basee a Guichen ».

> **A reporter en base.** Ce texte vit dans le contenu administrable
> `page:a-propos`. `SeedContent/a-propos.md` n'alimente que le **premier**
> amorcage (`SeedMissingAsync`) : sur un environnement deja amorce, la phrase
> doit etre saisie via le back-office des contenus administrables. Le
> deploiement du code ne la fera pas apparaitre.

## Verification

Sur le HTML reellement servi, et pas seulement sur les tests :

| Page | Titre servi |
|---|---|
| `/` | `Zachary IT \| Sauvegarde informatique a Guichen (35)` |
| `/a-propos` | `A propos \| Zachary IT` |
| `/offres` | `Offres de sauvegarde et stockage a Guichen \| Zachary IT` |
| `/wiki` | `Wiki \| Zachary IT` |

Une seule occurrence de la marque partout. Canonical, `og:site_name`,
`robots` et les deux blocs JSON-LD ont ete controles sur `/`.

Le contrat a ete valide par mutation : `WebSite.name` remis sur la raison
sociale, puis marque dupliquee dans le titre — les deux echouent avec le bon
message.

## Hors perimetre

- **`/wiki/article/<slug>` repond 200 sur `www`** alors que la canonical des
  articles pointe vers `https://wiki.zacharyhounsa.ovh/article/<slug>` (forme
  egalement publiee au sitemap). Le duplicata est neutralise par la canonical,
  l'impact est faible ; corriger suppose de trancher entre 301 et 404 dans
  `proxy.ts`, avec les tests associes.
- **Canonical d'accueil sans slash final** (`https://www.zacharyhounsa.ovh`)
  quand le sitemap emet `https://www.zacharyhounsa.ovh/`. Ecart connu, deja
  qualifie de faux positif : Next.js normalise ainsi la canonical resolue
  depuis `metadataBase`.
- Sur un article wiki introuvable, deux `<meta name="robots">` sont emis
  (`noindex` et `noindex, nofollow`). Directives concordantes, prealable a
  cette version.
