# Billing V2.1 — composants tarifaires et fulfillment

## Droit contractuel et prix

Un `billing_v2_subscription_item` represente un seul droit achete et une seule
cible de fulfillment/provisioning. Un service avec MRR et frais de setup porte
donc plusieurs lignes dans `billing_v2_subscription_item_price_components`, pas
plusieurs items.

- `legacy_single` : les colonnes historiques de l'item sont projetees comme une
  composante virtuelle. Les abonnements existants ne sont ni backfilles ni
  reinterpretés.
- `componentized` : les composants snapshotes sont la seule autorite
  financiere. Les anciennes colonnes sont un miroir de compatibilite.
- La vue `billing_v2_subscription_item_effective_price_components` est le point
  de lecture SQL commun. Les nouveaux chemins financiers ne doivent pas joindre
  directement le prix miroir d'un item componentized.

Un setup `one_time` est consomme atomiquement avec sa `BillingEventLine`. La
contrainte de debit ne bloque pas les references futures d'avoir ou d'ajustement
vers la meme composante. Un renouvellement ne lit que les composants `monthly`
actifs a la date de debut du cycle facture.

## Transition et changements

Un item V2.0 reste `legacy_single`. A sa premiere modification, il est borne
dans le temps et son successeur est componentized. Aucun setup passe n'est
devine ni facture a nouveau. Un frais ponctuel de changement doit etre declare
explicitement par `charge_trigger = subscription_change`.

Ainsi, VPS-CLOUD M -> L ne recree pas de setup initial. Le nouveau tier ne peut
porter une ligne ponctuelle que si une regle commerciale de changement existe.

Le modele reserve `charge_trigger = subscription_change` pour ces frais
ponctuels, mais ils sont **NOT_SUPPORTED en V2.1** : toute demande qui en
resout un est refusee avant ecriture. Leur prise en charge future devra creer
la `BillingEventLine` et la consommation one-time atomiquement dans la meme
transaction ; aucun contournement ni pseudo-consommation n'est autorise.

## Fulfillment

`billing_v2_subscription_item_fulfillment` est distinct de
`billing_v2_subscription_item_provisioning` : le paiement donne le droit mais
ne prouve pas la livraison. Les etats sont `pending`, `in_progress`,
`fulfilled`, `failed`. Les backends VPS restent commerciaux/operationnels et ne
sont jamais exposes comme produit public.

Les specifications `VPS-CLOUD` sont des attributs commerciaux administrables
du catalogue, jamais des capacites codees dans un backend ou dans le portail.
L'etat produit actuel est :

- `S` / Small : 2 vCPU, 2 GiB RAM, 60 GiB de stockage ;
- `M` / Medium : 4 vCPU, 8 GiB RAM, 160 GiB de stockage ;
- `L` / Large : 8 vCPU, 16 GiB RAM, 320 GiB de stockage ;
- `XL` : 16 vCPU, 32 GiB RAM, 640 GiB de stockage.

Ces valeurs proviennent des attributs `vcpu_count`, `ram_gib` et `disk_gib`
de `billing_v2_service_tier_attributes`. Elles sont rendues reproductibles par
la migration 081, qui ne fait qu'inserer les attributs absents. Le backend
reste `MANUAL` pour le fulfillment : afficher ou commander un palier ne prouve
pas sa livraison automatique.

## Readiness

Les migrations 066–069 ne rendent aucune capacite automatiquement disponible.
Les services Zachary IT sont visibles mais non commandables par defaut ;
`DOMAIN-MANAGED` reste sur devis. Stripe, providers VPS et provisioning reel
restent hors activation tant que leurs gates et preuves de bout en bout ne sont
pas completes.

## Frontieres de durabilite des changements

La demande de changement et, pour un upgrade, son `upgrade_charge`, sont
ecrits dans une meme transaction : un crash avant commit ne laisse rien ; apres
commit, le rejeu par cle d'idempotence retrouve la meme intention. Le settlement
est une transaction financiere distincte. L'application contractuelle ferme
l'ancien item, cree le successeur et ses composants, avance la version CAS,
marque le changement applique et ecrit l'outbox recurring dans une seule
transaction : un crash avant commit annule tout ce groupe.

Le dispatcher Stripe reclame ensuite l'outbox dans une transaction SQL courte,
avec une lease. Une ligne `processing` dont la lease expire est reclaimable ;
la mutation reste dedupliquee par la cle d'idempotence. L'application d'un
downgrade utilise la meme transaction contractuelle et conserve toujours
`effective_at` comme date historique du successeur, meme apres reprise tardive.
