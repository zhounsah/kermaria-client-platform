# v2.1.0 — refonte de la vitrine et constructeur de pages

**Statut au 7 octobre 2026 : version candidate, non taguée et non livrée en
production.** La production reste sur `v2.0.3.2`. Le numéro `v2.1.0` est
retenu pour préparer la livraison ; le commit, le tag, les paquets officiels
et la fenêtre de bascule restent à confirmer après la recette commune.

## Contenu prévu

- Parcours public réécrit pour les particuliers, associations et professionnels :
  accueil, services, offres, tarifs, diagnostic, inscription, panier et étapes
  avant paiement. Le pied de page regroupe contact, espace client et mentions
  légales. Les prix et les possibilités de commande restent ceux de Billing V2.
- Constructeur de pages des espaces public, client et administration : blocs
  éditoriaux et modules métier réordonnables, aperçu, médiathèque d'images,
  publication validée immédiatement, historique et restauration. Les modules
  indispensables restent obligatoires ; les contenus déjà administrés gardent
  leur éditeur d'origine. Les formulaires ajoutés dans le constructeur utilisent
  uniquement des actions prédéfinies.
- Page publique « Demander mes données », formulaire et suivi dans l'espace
  client, traitement et remise de réponse dans l'administration, documents
  privés et notifications. Aucune pièce d'identité n'est demandée d'office.
- Option d'approbation automatique des inscriptions standard après vérification
  de l'e-mail. Elle est désactivée par défaut, administrable, et le mode manuel
  reste disponible. Le modèle par défaut du courriel de vérification décrit
  les deux suites possibles sans promettre une revue manuelle dans le mode
  automatique. Les parcours particuliers existants gardent leurs règles.
- Mise à jour de Next.js vers `16.3.8` et des dépendances assorties.

## Schéma et architecture

Migrations additives `099_data_subject_requests`, `100_page_builder` et
`101_signup_auto_approval_state`. Elles sont déjà appliquées à
`BASE-SQL-01.home.bzh / kermaria_dev`, après une sauvegarde physique préparée.
**La base de production `BASE-SQL-01.home.bzh / kermaria` n'a reçu aucune de ces
migrations.** Elle exige une autorisation explicite sur ce couple hôte/base
avant toute connexion ou sauvegarde ciblée.

Le flux reste `browser → WEBPORTAL/BFF → API-INTERNAL → MariaDB`. L'API privée
conserve les contrôles de session, de permission et de données client ; les
prix, commandes et paiements restent gérés par Billing V2.

## Preuves disponibles en DEV

- `npm run validate`, builds Web et API, contrats ciblés et smoke tests API :
  réussis sur l'instantané isolé de la dernière passe. La validation complète
  a été relancée sur le worktree de préparation le 2026-10-07 et a réussi sans
  `APP_ENV` global. `git diff --check` et le contrôle des secrets de la mémoire
  commune : réussis.
- Publication, refus d'une page incomplète, conflit de version et restauration
  vérifiés sur MariaDB DEV pour des pages publiques. Une publication puis
  restauration de `/admin/catalog` a aussi été vérifiée via le BFF admin
  connecté, avec refus `400` si l'éditeur métier est retiré. Demandes de
  données, réponse, notification et fichier privé vérifiés avec un compte
  fictif. Les accès sans session et les accès croisés admin/client sont
  refusés (`401`/`403`). Une demande Outlook créée en DEV est invisible au
  premier client fictif ; le compte Gmail distinct voit une liste vide et un
  `404` sur cette demande.
- L'historique des mises en page et la liste de la médiathèque appliquent aussi
  `content.publish` côté API. Le correctif est livré en DEV et la lecture avec
  le compte administrateur autorisé fonctionne ; le cas d'un administrateur
  sans ce droit reste à exercer en environnement réel.
- API DEV SRV-13 et WebPortal DEV SRV-12 actifs. Les pages publiques révisées
  répondent 200 ; fiche d'offre, panier et revue avant paiement ont un titre
  principal et ne débordent pas à 390 px. Une archive Web incorrecte a été
  retirée du service DEV après des 404 sur ses assets ; l'archive corrigée
  sert les scripts, les images et le panier. Détails, empreintes et retour
  arrière : [DEV_UX_CMS_2026-10-05.md](DEV_UX_CMS_2026-10-05.md).

Les premiers paquets DEV ont été construits avant l'inscription de `2.1.0`
dans les métadonnées source. Le dernier paquet Web DEV affiche `v2.1.0`, mais
provient encore du worktree de préparation. Les paquets officiels devront
être reconstruits depuis le tag exact après autorisation.

Le script `Install-WebportalDev.ps1` a été corrigé : sous PowerShell 5.1, son
ancien chemin de secrets calculé dans la liste des paramètres échouait avant
le début du script. Il le résout maintenant dans le corps du script et vérifie
que le fichier DEV existe. La syntaxe et la cible par défaut ont été vérifiées ;
le dernier déploiement DEV avait utilisé explicitement ce chemin.

## Recette et décision de livraison

La revue des formulations, offres réellement proposées et textes juridiques
appartient au propriétaire du site. La recette avec les comptes de démonstration
DEV a confirmé le mode manuel, la portée client des demandes et la publication
du constructeur via BFF. Avec les boîtes autorisées, l'inscription Outlook
a été vérifiée et approuvée manuellement ; un alias Gmail fictif a été
approuvé automatiquement après vérification de l'e-mail. Les deux comptes
se sont connectés après définition de leurs mots de passe par le titulaire.
Le lien automatique répété n'a créé ni seconde approbation ni second e-mail.
Les demandes de deux clients distincts sont isolées. La reprise après échec
partiel réel d'envoi reste à éprouver ; le smoke test couvre le renvoi.
L'aperçu de l'accueil dans l'éditeur admin a été vu dans une session connectée,
puis corrigé pour garder le texte lisible sur la photo. Le titre du brouillon
a été modifié temporairement et restauré sans publication. La revue visuelle
des autres espaces du constructeur et du catalogue admin reste à faire ; les
tableaux de bord et profils des deux nouveaux comptes ont été observés.

Le propriétaire a autorisé l'emploi de ses boîtes Gmail et Outlook pour ces
essais. Le premier jeton hCaptcha avait expiré, puis des accords spécifiques
ont permis les deux inscriptions fictives. Les e-mails ont été reçus dans les
deux boîtes. L'allowlist DEV et le mode manuel sont restaurés après la recette.
L'API DEV porte le correctif du texte d'e-mail ; les paquets officiels v2.1.0
devront l'inclure.

Le propriétaire a autorisé le commit, le tag `v2.1.0`, le push et le
déploiement **à condition que la revue métier soit validée**. La validation de
cette revue et la fenêtre de livraison restent à confirmer. Il faut aussi
approuver explicitement `BASE-SQL-01.home.bzh / kermaria` pour sa sauvegarde et
ses migrations. La [liste propriétaire](A_FAIRE_UTILISATEUR_UX_CMS_2026-10-06.md)
regroupe ces décisions. La note présente restera marquée « candidate » tant
que les preuves de la release immuable et de la production n'y auront pas été
ajoutées.

## Séquence et retour arrière prévus

Après la décision, rapprocher le worktree des seuls fichiers du chantier,
valider et figer le commit/tag exact. Construire et contrôler les archives
API/Web depuis cette référence, puis refaire une passe DEV avec ces paquets.
Pour la production : vérifier les services et leurs empreintes, sauvegarder la
base approuvée, appliquer explicitement les migrations manquantes, déployer
l'API privée sur SRV-13 puis le WebPortal sur SRV-12, et vérifier les routes,
la santé et les journaux sur chaque hôte.

Conserver les anciens dossiers API et la cible précédente du lien Web pour un
retour applicatif. Les migrations étant additives, ne pas supprimer leurs
tables ni leurs données dans un retour arrière automatique. Une restauration
SQL éventuelle demande un plan distinct et une décision explicite.
