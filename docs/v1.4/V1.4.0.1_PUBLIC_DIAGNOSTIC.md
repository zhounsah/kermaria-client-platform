# v1.4.0.1 - Diagnostic public sur Billing V2
Date : 2026-08-20
## Objectif
Le questionnaire `/diagnostic` conserve ses quatre etapes et son UX, mais son
moteur commercial est migre de l'ancien catalogue de packs vers Billing V2.
Avant ce hotfix, le diagnostic dependait de :
- `getPublicCommercialCatalog()` ;
- `getPublicPackCatalogContent()` ;
- `ResolvedPublicPackManifest` ;
- `CatalogConfigurationInput` ;
- seuils legacy de stockage/utilisateurs ;
- sortie `/configurer`.
Apres v1.4.0.1, le flux est :
```text
/diagnostic
  -> DiagnosticAnswers
  -> BillingV2PublicSelection | requires_quote
  -> POST /api/formules/devis
  -> /formules/{preset}?selection V2 complete
  -> signup
  -> activation
  -> login
  -> /formules/reprendre
  -> Stripe
  -> provisioning Billing V2
```
## Autorite commerciale
`public-diagnostic.ts` ne calcule aucun montant et ne lit aucun prix. Il ne
manipule que des codes catalogue et des paliers publics. Le prix affiche dans le
resultat provient exclusivement de `/api/formules/devis`, qui appelle le moteur
Billing V2 existant (`quoteBillingV2Formule` / `BillingV2PricingEngine`).
Le navigateur ne devient donc jamais une seconde autorite tarifaire.
## Selection publique
La recommandation standard produit une `BillingV2PublicSelection` complete.
L'engagement initial est `FLEX`, en `monthly`; l'utilisateur peut ensuite
modifier engagement et options dans `/formules/{preset}`.
Bornes retenues :
- stockage personnel : 16, 32, 64, 128 ou 256 Go ;
- plus de 256 Go : `requires_quote` ;
- 1 a 11 utilisateurs totaux : selection publique ;
- 12 utilisateurs ou plus : `requires_quote` ;
- `additionalUsers = totalUsers - 1`, avec maximum public de 10.
Les anciennes regles `> 64 Go`, `> 2 utilisateurs`, RDS multi-utilisateur ou
RDS avec plus de 32 Go ne sont plus bloquantes lorsqu'une composition V2 peut
representer le besoin.
Une structure peut partir du preset Pro / Association puis ajouter le bureau
Windows. Un particulier peut recevoir un preset RDS avec un palier personnel
superieur au standard historique.
## Sortie et reprise
Le CTA utilise `billingV2SelectionToSearchParams()` et dirige vers
`/formules/{preset}` avec la selection V2 complete. Le tunnel deja livre en
v1.4.0.0 est reutilise sans changement : signup, activation, login,
`/formules/reprendre`, checkout Stripe puis provisioning.
La selection V2 est deja persistable dans
`signup_pending.catalog_configuration_snapshot_json`; aucune migration SQL
n'est necessaire.
## Legacy preserve
`/configurer`, le catalogue legacy et les types de packs historiques ne sont
pas supprimes globalement. Ils restent utilises par d'autres parcours. Seul le
diagnostic est decouple de ces dependances.
