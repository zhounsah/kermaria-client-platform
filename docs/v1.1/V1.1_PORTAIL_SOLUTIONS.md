# V1.1 - Portail public des solutions client

## Objectif

Publier sur le site vitrine une page libre-service `/solutions` qui recense
les services accessibles aux clients (bureau a distance, espace de fichiers,
etc.). Chaque entree est une tuile cliquable : nom, logo, phrase courte,
et un lien qui ouvre le service.

La page est **entierement administrable depuis le back-office** : ajout,
modification, suppression d'une tuile, changement du nom ou du logo, ordre
d'affichage, et texte d'en-tete. Aucune intervention sur le code n'est
necessaire pour faire evoluer cette page.

> **Hors index depuis la `v1.1.12`.** La page reste publique, atteignable
> sans session et liee depuis la coquille : seule son indexation change. Un
> portail d'acces client (~115 mots, aucun `h2`) n'apporte aucun trafic et
> tire vers le bas la qualite moyenne percue du site. Elle porte donc
> `robots: { index: false, follow: true }` et sort du sitemap — mais **pas**
> du `Disallow` de `robots.txt`, sinon la directive ne serait jamais lue.
> Detail : [`V1.1.12_SEO_BALISAGE.md`](V1.1.12_SEO_BALISAGE.md).

## Architecture retenue

Flux public (aucune session requise) :

```text
visiteur -> /solutions           -> WEBPORTAL (rendu serveur) -> API-INTERNAL /internal/portal/client-solutions
visiteur -> logo d'une tuile     -> WEBPORTAL /api/solutions/{id}/logo -> API-INTERNAL /internal/portal/client-solutions/{id}/logo
```

Flux admin :

```text
admin -> /admin/solutions        -> WEBPORTAL /api/admin/client-solutions*         -> API-INTERNAL /internal/admin/client-solutions*
admin -> upload logo             -> WEBPORTAL /api/admin/client-solutions/{id}/logo -> API-INTERNAL /internal/admin/client-solutions/{id}/logo
```

`WEBPORTAL` n'accede jamais directement a MariaDB : la frontiere habituelle
`browser -> WEBPORTAL/BFF -> API-INTERNAL -> MariaDB` est respectee.

## Modele de donnees

Migration `041_client_solutions_portal.sql`.

`client_solution_portal_settings` (une seule ligne, cle `default`) :

| Colonne       | Role                                          |
| ------------- | --------------------------------------------- |
| `eyebrow`     | surtitre affiche au-dessus du titre           |
| `title`       | titre H1 de la page (obligatoire)             |
| `description` | paragraphe d'introduction                     |
| `footer_note` | note affichee sous la grille                  |

`client_solutions` (une ligne par tuile) :

| Colonne                                  | Role                                        |
| ---------------------------------------- | ------------------------------------------- |
| `slug`                                   | identifiant d'URL unique, derive du nom     |
| `title`                                  | nom affiche sur la tuile                    |
| `tagline`                                | phrase courte optionnelle                   |
| `target_url`                             | lien absolu `http(s)` ouvert au clic        |
| `opens_in_new_tab`                       | ouverture dans un nouvel onglet             |
| `status`                                 | `published` (visible) ou `draft` (masquee)  |
| `display_order`                          | ordre croissant, puis titre                 |
| `logo_bytes` + metadonnees               | logo stocke en base (voir ci-dessous)       |

### Pourquoi le logo est stocke en base

Contrairement aux binaires de la V0.37, les logos ne sont pas stockes sur
disque :

- ils sont petits (512 Ko maximum) et peu nombreux ;
- aucun repertoire supplementaire n'est a creer ni a sauvegarder sur le
  serveur : la sauvegarde MariaDB existante les couvre deja ;
- aucune variable d'environnement supplementaire n'est requise.

Types acceptes : `image/png`, `image/jpeg`, `image/webp`, `image/svg+xml`.
Le controle est applique deux fois, cote BFF et cote `API-INTERNAL`.

Sans logo, la tuile affiche automatiquement les initiales du nom : une
solution reste donc presentable des sa creation.

## Regles de visibilite

Une tuile apparait sur `/solutions` si et seulement si son `status` vaut
`published`. Le logo suit la meme regle : `/api/solutions/{id}/logo` repond
`404` pour une solution en brouillon. Une tuile peut donc etre preparee
completement avant d'etre rendue publique.

## Securite

- La page et la route de logo sont publiques par construction : ce sont des
  medias de vitrine, pas des donnees client. Aucune information de compte
  n'y transite.
- Le logo est servi avec `X-Content-Type-Options: nosniff`,
  `Content-Disposition: inline` et
  `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; sandbox`.
  Un SVG televerse ne peut donc pas executer de script.
- Les liens sortants ouverts dans un nouvel onglet portent
  `rel="noopener noreferrer"`.
- Seules les URL absolues `http`/`https` sans identifiants integres sont
  acceptees (`javascript:` et `data:` sont refuses).
- Toutes les mutations passent par une session `internal_admin` avec jeton
  CSRF, et sont journalisees dans l'audit
  (`client_solution.create`, `client_solution.update`,
  `client_solution.delete`, `client_solution.logo.upload`,
  `client_solution.logo.delete`, `client_solution_portal.update`).

## Utilisation cote back-office

1. Ouvrir **Administration > Activite commerciale > Portail solutions**.
2. Ajuster l'en-tete de page (surtitre, titre, introduction, note de bas de
   page) puis enregistrer.
3. « Nouvelle solution » : renseigner le nom, le lien du service, une phrase
   courte optionnelle, l'ordre d'affichage, et televerser le logo.
4. Laisser l'etat sur **Brouillon** le temps de verifier le rendu, puis
   passer sur **Publiee**.
5. Pour retirer une entree : ouvrir sa fiche, « Supprimer la solution »
   (suppression definitive) ou repasser en brouillon pour la masquer sans
   la perdre.

L'identifiant d'URL est genere automatiquement a partir du nom ; il peut
etre force manuellement et doit rester unique (conflit signale par un
message explicite).

## Verification

```bash
npm run test:client-solutions
```

Le script `apps/webportal/scripts/verify-client-solutions-contract.mjs`
verifie le contrat de bout en bout : types partages, validation BFF,
absence de session sur la route publique, en-tetes de securite du logo,
filtrage sur `published`, endpoints et evenements d'audit, horodatages UTC
et migration MariaDB.

Recette manuelle minimale :

1. creer une solution en brouillon, verifier qu'elle **n'apparait pas** sur
   `/solutions` ;
2. la passer en publiee, verifier la tuile, le logo et le lien ;
3. supprimer le logo, verifier le repli sur les initiales ;
4. supprimer la solution, verifier la disparition de la tuile.

## Reprise MariaDB

La migration `041` est additive et idempotente
(`CREATE TABLE IF NOT EXISTS`, `INSERT IGNORE`). Elle s'applique
**uniquement** par la commande explicite
`dotnet run --project apps/api-internal/Kermaria.ApiInternal.csproj -- --apply-migrations`.

Aucun DDL n'est execute au fil des requetes : le compte applicatif
`kermaria_api` n'a deliberement aucun droit de schema, et une tentative
echouerait des la table de suivi `schema_migrations` (voir la panne du
centre de telechargements corrigee en 1.1.9.2). `ClientSolutionSchemaEnsurer`
se contente donc de verifier en lecture seule, via
`information_schema.tables`, que `client_solutions` et
`client_solution_portal_settings` existent ; leur absence donne un
`503 CLIENT_SOLUTIONS_SCHEMA_UNAVAILABLE` explicite cote administration.

La page publique `/solutions`, elle, degrade proprement : si le schema
n'est pas encore applique, elle affiche l'en-tete par defaut et le message
« aucune solution publiee » au lieu d'une erreur.
