# V1.1 — Comptes de démonstration et d'essai personnalisés

> Statut : **conception validée** (rédigé le 2026-08-03, points ouverts tranchés
> le même jour). Fonctionnalité **post-V1.0** (la mise en prod V1.0 est débloquée
> depuis la livraison du R740xd ≈ 2026-07-23). Idée d'origine suggérée par le père
> de l'utilisateur : proposer des comptes de démonstration adaptés au besoin de
> chaque client.

## 1. Objet

Permettre à l'administrateur de créer, à la demande, des **comptes de
démonstration ou d'essai personnalisés**, de façon **scalable** (peu de travail
par démo) et **sûre** (aucune fuite vers les intégrations réelles quand ce n'est
pas voulu).

Trois usages, un seul mécanisme :

1. **Démo commerciale prospect** — montrer à un prospect « son » back-office
   pré-rempli. Éphémère, jetable, jamais facturé.
2. **Essai réel restreint** — accès réellement fonctionnel mais borné (ex. 5 Go
   de stockage, session RDS plafonnée), avec expiration.
3. **Vitrine interne / tests** — proche de l'existant mais rendu personnalisable.

## 2. Décisions actées (2026-08-03)

| Sujet | Décision |
|---|---|
| Registre des profils | **Table administrable** (`demo_profiles`), éditable depuis l'admin sans redéploiement. |
| Auto-expiration | **Les deux** : service de fond dans l'API interne (SRV-13) **+** tâche planifiée Windows en filet de sécurité. |
| Collection RDS d'essai | **Réutiliser Clients-1 (SRV-30)** avec RemoteApp/bureau gated `GG_DEMO_RDS`. |
| Cloisonnement réseau | **VLAN dédié 64 — `10.35.64.0/24` « Clients Démo »**. |
| Conversion essai → client | **Bascule sur place** : `is_demo=false`, rattachement à une vraie offre, migration de l'identité AD hors OU DEMO, levée des restrictions. |
| Numéro de version | **V1.1** (post-V1.0). |
| Déclenchement provisioning | Chaîne privée KoXo existante, sur événement « mot de passe rempli » — **uniquement pour les comptes `trial`** (jamais `showcase`). |

  (`apps/api-internal/Data/Migration/MariaDbMigrationRunner.cs`), gardée par

  (`Migrations/MariaDb/seed_development.sql`). Non personnalisable. → remplacée

- **L'accès plateforme = appartenance à des groupes AD** (`GG_RDS`, `GG_VPN`,
  `GG_NextCloud`…) via `SubscriptionProvisioningRuntimeConfiguration.cs`.
  Provisionner = ajouter au groupe ; révoquer = retirer. Déjà construit.
- **Catalogue expressif** : `commercial_offers.technical_service_references` et
  `provisioning_group_sam_account_names` (migration `033`). Un « essai » peut se
  modéliser comme une offre spéciale.
- **Mode mock / `MockNotice`** : socle d'inertie pour les usages 1 et 3.
- **Chaîne KoXo privée** (`docs/koxo-sync.md`) :
  `webportal (SRV-12) → api-internal (SRV-13) → webhook privé SRV-21 → PowerShell
  → KoXo`, déclenchée à l'initialisation du mot de passe client. Synchronise les
  **identités/métadonnées** (7 champs), **pas** l'appartenance aux groupes.

## 4. Principe directeur : deux axes indépendants

Séparer **ce que le compte contient** de **ce qu'il a le droit de faire**.

- **Axe A — Contenu** : services, factures d'exemple, téléchargements,
  abonnements. Piloté par **template** *ou* **composition à la carte**.
- **Axe B — Capacités** : matrice de politique par compte (email / BPCE /
  paiement / AD / stockage / RDS), du mode inerte au réel plafonné.

> **Profil de démo = Template (A) + Matrice de capacités (B) + Cycle de vie.**

Ajouter un type de démo = **de la donnée** (une ligne de `demo_profiles`), pas du
code.

## 8. Usage 2 — accès réel restreint : ancrage sur l'infra R740xd

Infra cible **live** (VM actives depuis ≈ 2026-07-23). Points d'ancrage :

### 8.1 Identités et groupes — `clients.home.bzh` (SRV-21 / KERMARIA-DC-05)

- Groupes de démo **dédiés par service**, convention **ASCII sans accent**
  (`sAMAccountName` ≤ 20 car. + pipeline CSV KoXo) : `GG_DEMO_RDS`,
  `GG_DEMO_VPN`, `GG_DEMO_NEXTCLOUD`.
- Les ajouter au dictionnaire de provisioning (`SUBSCRIPTION_PROVISIONING_*` /
  `AD_PROVISIONING_GROUP_DNS`) — pas de code de résolution nouveau. DN **réels
  confirmés** (OU `Groupes_TEST`, frère de `OU=Clients`) :
  - `CN=GG_DEMO_NEXTCLOUD,OU=Groupes_TEST,DC=clients,DC=home,DC=bzh`
  - `CN=GG_DEMO_RDS,OU=Groupes_TEST,DC=clients,DC=home,DC=bzh`
  - `CN=GG_DEMO_VPN,OU=Groupes_TEST,DC=clients,DC=home,DC=bzh`
- **Whitelister** `GG_DEMO_*` dans `AD_ALLOWED_GROUPS` (aujourd'hui limité à
  `TEST_SITE_WEB`), sinon le garde-fou d'écriture AD refusera l'ajout.
- ⚠️ **Roots autorisés à réconcilier** : les groupes étant sous `OU=Groupes_TEST`
  (hors `AD_CLIENTS_OU_DN`), le garde-fou `IsWithinAllowedRoots` (appliqué au DN du
  groupe *et* de l'utilisateur) impose d'**ajouter** `OU=Groupes_TEST` à
  `AD_ALLOWED_ROOTS` (sans retirer `AD_CLIENTS_OU_DN`, que le contrat exige d'y
  trouver exactement une fois) et de remonter `AD_REQUIRED_OU_ROOT` à la racine
  commune `DC=clients,DC=home,DC=bzh` (sinon `ConfigurationValid` retombe à faux et
  toute écriture AD est refusée). Voir `DEPLOYMENT_WINDOWS.md` §15.
- Comptes démo (identités utilisateur) : OU **créée automatiquement par KoXo**,
  `OU=CLI-DEMO,OU=CLIENTS,OU=Utilisateurs,OU=KoXoAdm,DC=clients,DC=home,DC=bzh`,
  déjà **sous** `AD_CLIENTS_OU_DN` → aucun ajout de root nécessaire pour les comptes.
- ⚠️ **Groupes partagés ≠ groupes du client** : les `GG_DEMO_*` vivant hors de l'OU
  du client, l'appartenance doit passer par `IAdGroupProvisioner` (bind sur le DN
  complet de `AD_PROVISIONING_GROUP_DNS`). Le chemin par-client de
  `IActiveDirectoryService` les chercherait sous l'OU du client et échouerait.
- **Piège AD** : créer les `GG_DEMO_*` **dans `clients.home.bzh` en
  Domain-Local/Universal**, jamais comme groupes Global du domaine parent
  `home.bzh` — les Global du parent n'acceptent pas de membres du domaine enfant
  (contrainte déjà rencontrée sur les groupes historiques).
- **Provisioning** : via la chaîne privée existante, déclenché à
  l'initialisation du mot de passe, **pour les `trial` uniquement**.
- **Révocation à l'expiration** : **retrait AD direct** des `GG_DEMO_*` depuis
  SRV-13 (`svc_api_portal_ad`) — pas via KoXo (qui ne gère pas les groupes).

### 8.2 RDS — réutilisation de Clients-1 (SRV-30), gated

- **RemoteApp / bureau de démo publié sur la collection Clients-1 (SRV-30)**,
  réservé à `GG_DEMO_RDS` (décision §2 : pas de collection dédiée).
- **Limites de session natives** (choix acté, pas de « 2 h/jour » cumulé non
  natif) : durée max de session active + inactivité + fin de session
  déconnectée, via propriétés de collection / GPO ciblant `GG_DEMO_RDS`.
- Accès via **RD Gateway (SRV-27)** : RD CAP/RAP limitant `GG_DEMO_RDS` au seul
  périmètre démo.
- Profil plafonné via **UPD (SRV-28)**.
- ⚠️ Conséquence du partage d'hôte avec les vrais clients : compenser par le
  groupe dédié, les GPO de session, et le cloisonnement réseau VLAN 64 (§8.4).

### 8.3 Stockage — quota FSRM

- Le « 5 Go » est un libellé catalogue (`STOCK-PERSO-32`) sans enforcement
  applicatif. Limite réelle via **FSRM** sur le volume dédié **« Stockage
  dossiers personnels »** (RAID1), sur le dossier du compte démo.
- L'appli **stocke et transmet** `storage_quota_go` à la couche provisioning ;
  elle ne fait pas respecter le quota elle-même.

### 8.4 Réseau — VLAN dédié « Clients Démo »

- **VLAN 64 — `10.35.64.0/24` « Clients Démo »** (nouveau segment, décision §2),
  aux côtés des VLAN VPN 61/62/63. Paramètres confirmés : masque `255.255.255.0`,
  passerelle `10.35.64.254`, broadcast `10.35.64.255`, plage utilisable
  `10.35.64.1 – 10.35.64.254` (253 IP).
- Règles firewall : accès limité aux seules ressources de démo (collection RDS
  gated, dossier perso quota, éventuellement `GG_DEMO_VPN`) ; isolé du réseau
  clients réel (240) et serveurs (100) au strict nécessaire.

## 9. Isolation et inertie (usages 1 & 3) — non négociable

> **Contexte critique** : l'environnement tourne avec toutes les intégrations en
> **`live`** (BPCE, Stripe, PayPal, Email `live` + `EMAIL_LIVE_ALLOWLIST=*`, AD
> `controlled_write`). L'inertie **ne peut donc pas** s'appuyer sur des modes
> globaux non-live : elle doit être **imposée par le code, conditionnée à
> `customer.is_demo` / `demo_kind = showcase`**, à chaque point d'intégration.

Pour tout `customer` `is_demo` en mode `showcase`, couper les effets réels :

- **BPCE** : aucune émission fiscale (`bpce_invoices`).
- **Email** : aucun envoi SMTP réel (OVH live).
- **Paiement** : aucun débit Stripe/PayPal.
- **AD/KoXo** : aucun provisioning réel, **chaîne KoXo non déclenchée** même à
  l'initialisation du mot de passe.

Exclusion **systématique** des comptes `is_demo` des vues admin métier réelles,
du reporting et de la facturation (garde-fou côté requêtes, pas seulement UI).

## 10. Cycle de vie

1. **Création** depuis l'admin (SRV-12) : écran « Nouveau compte démo » →
   **template** *ou* **composition à la carte** ; durée de vie.
2. **Provisioning** : selon la matrice ; pour `trial`, chaîne KoXo à « mot de
   passe rempli ».
3. **Expiration** : `demo_expires_at` détectée par **service de fond SRV-13
   (démarrage + périodique)** doublé d'une **tâche planifiée Windows** (filet).
   → retrait AD direct des `GG_DEMO_*`, désactivation du compte.
4. **Purge** : suppression par lot des démos expirées (contenu + identité), sans
   toucher aux clients réels.
5. **Conversion essai → réel** (décision §2 : **bascule sur place**) :
   `is_demo=false`, rattachement à une vraie offre, **migration de l'identité AD
   hors OU DEMO** (et hors groupes `GG_DEMO_*` vers les vrais groupes), levée des
   restrictions FSRM/RDS/réseau. Contenu et historique conservés.

## 11. Sécurité et conformité

- **Accès réel à un prospect = vrai logon.** Cloisonnement OU dédiée + groupes
  `GG_DEMO_*` + VLAN 64 + expiration courte. Ne jamais réutiliser les groupes
  clients réels pour un prospect.
- Le partage de l'hôte RDS Clients-1 (§8.2) est un risque accepté, compensé par
  groupe/GPO/VLAN ; à réévaluer si un prospect doit exécuter du code arbitraire.
- Traçabilité : création / expiration / purge / conversion dans `audit_logs`.
- Interdiction d'ensemencer un template à partir de données clients réelles non
  anonymisées.
- `demo_expires_at` en UTC (convention projet).

## 12. Points restants (mineurs, à trancher en implémentation)

2. **Périodicité** du service de fond d'expiration (ex. horaire) et fréquence de

3. **Migration d'identité AD** lors de la conversion (renommage/déplacement

## 16. Lot 4 — conversion essai → réel (livré)

### 16.1 Principe

**Bascule sur place** : le compte garde son identité AD, son mot de passe, son
profil et tout son contenu. On ne recrée jamais d'identité — seules les
restrictions de démonstration sont levées.

- **Migration `039_v11_demo_conversion.sql`** : `demo_converted_at`,
  `demo_converted_by_user_id`, `demo_source_profile_key`, + index.
- **`DemoConversionService`** — `POST /internal/admin/demo/accounts/{ref}/convert`
  (`admin.demo.write`), bouton « Convertir » sur `/admin/demo`.

### 16.2 Ordre des opérations (volontaire)

**L'annuaire d'abord, la base ensuite.** Si l'AD échoue à mi-parcours, la bascule
en base n'a pas lieu et l'opération reste **rejouable telle quelle** (les retraits
et ajouts de groupes sont idempotents). L'ordre inverse laisserait un client
« réel » sans accès réel.

1. retrait des `GG_DEMO_*` ;
2. ajout des groupes réels de l'offre cible (facultative) ;
3. déplacement de l'identité hors de l'OU de démonstration ;
4. en base : `is_demo = FALSE`, marqueurs de démo remis à `NULL`.

Remettre `demo_profile_id` / `demo_kind` / `demo_expires_at` à `NULL` est ce qui
sort définitivement le compte du balayage d'expiration et de la purge ; la
provenance est donc conservée dans `demo_source_profile_key`.

**Idempotence** : `demo_converted_at` sert de garde — un rejeu ou un double clic
renvoie `DEMO_CONVERSION_ALREADY_DONE` sans rien refaire.

### 16.3 Déplacement d'OU — extension nécessaire

> **Remplacé par le lot 5 (§17).** Le déplacement d'OU n'est plus effectué par
> l'application : il est délégué à KoXo via le champ `GroupeSecondaire` de
> l'export. `TargetOrganizationalUnitDn` est **conservé comme repli** tant que la
> première conversion réelle n'a pas confirmé que KoXo relocalise bien une
> identité existante. La section ci-dessous décrit donc un mécanisme encore
> présent dans le code, mais inactif par défaut.


`MoveUserAsync` ne visait que les conteneurs du schéma applicatif (`Users` /
`Disabled`), reconstruits pour une référence client. Or les comptes de démo vivent
dans `OU=CLI-DEMO,…` — une arborescence **créée par KoXo**, que l'application ne
sait pas reconstruire.

`MoveAdUserRequest` accepte donc désormais un **`TargetOrganizationalUnitDn`**
explicite, validé contre `AD_ALLOWED_ROOTS` — le même garde-fou que les DN de
groupes partagés. Les modes `Users`/`Disabled` existants sont inchangés.

Configuration : **`DEMO_CONVERSION_TARGET_OU_DN`**. Non renseignée, l'étape de
déplacement est volontairement neutre et le cloisonnement reste porté par les
seuls groupes.

### 16.4 Refus explicites

| Situation | Code |
|---|---|
| Référence hors périmètre démo | `DEMO_CONVERSION_NOT_A_DEMO` |
| Compte `showcase` (aucun accès réel à basculer) | `DEMO_CONVERSION_NOT_A_TRIAL` |
| Identité AD introuvable | `DEMO_CONVERSION_NO_IDENTITY` |
| Échec AD partiel — base non modifiée, rejouable | `DEMO_CONVERSION_PARTIAL` |

### 16.5 Frontière assumée

Ce service traite l'**accès technique** (groupes AD, emplacement de l'identité).
L'acte **commercial** — souscription, facturation — reste le parcours existant et
n'est pas dupliqué ici.

## 17. Lot 5 — réservation du code de groupe KoXo (livré)

### 17.1 Le partage des rôles

Deux domaines, deux maîtres, sans recouvrement :

| Domaine | Maître | Mécanisme |
|---|---|---|
| **Permissions** (groupes `GG_*`) | l'**API** | écriture AD directe depuis SRV-13, synchrone |
| **Arborescence** (OU de l'identité) | **KoXo** | champ `GroupeSecondaire` du CSV d'export |

Le CSV fait autorité lors d'une synchronisation, **mais ne porte pas les
permissions**. Une synchronisation ne peut donc pas défaire une révocation faite
par l'API — point vérifié explicitement, car l'inverse aurait rendu à un essai
expiré ses accès sans aucun signal.

### 17.2 Le levier : `GroupeSecondaire`

KoXo place l'identité dans l'OU nommée d'après ce champ, **et crée l'OU si elle
n'existe pas**. C'est le seul levier de la conversion côté annuaire.

| Phase | `GroupeSecondaire` publié |
|---|---|
| Essai en cours | `CLI-DEMO` — OU de démonstration commune |
| Après conversion | le code `CLI-XXXXXX` réservé à la création |
| Client réel ordinaire | sa référence, qui nomme déjà son OU |

### 17.3 Réservation à la création, publication à la conversion

Un code définitif `CLI-XXXXXX` est alloué **dès la création** du compte de démo,
puis **retenu** : tant que le compte est en démonstration, l'export publie
`CLI-DEMO`. La conversion se contente de publier le code réservé.

L'intérêt n'est pas cosmétique : `customers.external_reference` **ne change
jamais**. Sans cette réservation, convertir imposerait de renommer la référence
client, ce qui cascaderait sur les factures, les documents et les abonnements.

Le tirage vérifie l'unicité sur **les deux** colonnes (`external_reference` et
`koxo_group_reference`) : un code réservé devient une référence d'OU à la
conversion, les deux espaces sont donc confondus.

Les comptes créés avant ce lot sont rattrapés à la conversion ; l'écriture est
conditionnée à `koxo_group_reference IS NULL`, de sorte qu'un code déjà réservé
n'est jamais écrasé — l'écraser déplacerait une OU déjà créée par KoXo.

### 17.4 Correctif — les vitrines partaient dans le pipeline réel

L'export ne filtrait que `status = 'active'`. Les comptes **`showcase`**, dont
l'inertie totale est un point non négociable (§9), étaient donc transmis au
pipeline d'identités réelles. Ils en sont désormais exclus ; les `trial` restent
exportés, puisqu'ils ont besoin d'une identité AD.

**Conséquence à surveiller** : le CSV faisant autorité, retirer une ligne est une
instruction, pas un silence. La disparition des vitrines de l'export peut amener
KoXo à désactiver ces identités à la prochaine synchronisation — comportement
probablement souhaitable, mais à constater plutôt qu'à supposer.

### 17.5 Reste à faire

de relire `customer_ad_links` : le DN y est figé à la création et mentirait
précisément dans le cas à détecter. Elle exige une résolution **en direct** dans

### 15.1 Ce que le code applique / déclenche

- **Migration `038_v11_demo_provisioning.sql`** : `customers.demo_provisioned_at`
  + `demo_revoked_at` (trace + idempotence de la révocation), index de balayage.
- **`DemoProvisioningService`** (`applies` + `triggers`) — l'appartenance aux
  `GG_DEMO_*` passe par **`IAdGroupProvisioner`** (bind sur le DN complet de
  `AD_PROVISIONING_GROUP_DNS`), car ce sont des groupes **partagés** hors de l'OU du
  client ; seule la désactivation du compte utilise le chemin par-client
  `IActiveDirectoryService.DisableUserAsync`. Si le DN d'un groupe n'est pas
  configuré, l'ajout est ignoré (log) et la révocation est déclarée **incomplète**
  (l'essai n'est pas marqué révoqué, le balayage suivant réessaie) :
  - `ProvisionTrialAsync` — **trial + `real_scoped` uniquement**. Ajout direct des
    groupes `GG_DEMO_*` si l'identité AD existe (sinon reporté `pending_identity`,
    rejoué au prochain passage) + déclenchement de la chaîne KoXo
    (`password_set`). **Garde-fou dur : `showcase` = no-op total**, quelle que
    soit la configuration globale.
  - `RevokeTrialAsync` — retrait direct des groupes `GG_DEMO_*` + désactivation du
    compte AD (`DisableUserAsync`).
- **Cycle d'expiration** (`applies`) : `DemoAccountService.RunExpirationSweepAsync`
  (révoque les essais échus **puis** purge) exécuté par :
  - `DemoAccountExpirationWorker` — service de fond SRV-13 (démarrage + horaire) ;
  - argument CLI `--run-demo-expiration` — **tâche planifiée Windows** (filet),
    script `deploy/Register-DemoExpirationTask.ps1` ;
  - endpoint `POST /internal/admin/demo/expire` (`admin.demo.write`) — déclenchement
    manuel ops.
- **Quota / RDS / VLAN** (`transmits`) : `storage_quota_go`, `rds_session_mode` et
  les groupes `GG_DEMO_*` du profil sont stockés et exposés ; l'enforcement reste
  FSRM/GPO/firewall (§8.3, §8.2, §8.4).
- **Admin** : la liste des comptes démo affiche le statut de cycle de vie
  (actif / expiré / révoqué) via `demo_revoked_at`.

### 15.2 Prérequis d'activation réelle (infra/config, hors code)

1. Créer les groupes `GG_DEMO_RDS` / `GG_DEMO_VPN` / `GG_DEMO_NEXTCLOUD` en
   **Domain-Local dans `clients.home.bzh`** (jamais Global du parent), OU
   **`OU=Groupes_TEST`** (emplacement réel confirmé, §8.1).
2. Renseigner `AD_PROVISIONING_GROUP_DNS` (DN de chaque `GG_DEMO_*`),
   **whitelister** ces groupes dans `AD_ALLOWED_GROUPS`, et **étendre
   `AD_ALLOWED_ROOTS`/`AD_REQUIRED_OU_ROOT`** pour couvrir `OU=Groupes_TEST`
   (§8.1) — sinon le garde-fou d'écriture AD refuse l'ajout. Vérifier ensuite
   avec `npm --prefix apps/webportal run test:signup`.
3. `svc_api_portal_ad` (SRV-13) autorisé à modifier l'appartenance des
   `GG_DEMO_*` + à désactiver les comptes de l'OU DEMO.
4. FSRM sur le volume « Stockage dossiers personnels », RemoteApp Clients-1 gated
   `GG_DEMO_RDS` + GPO de session, VLAN 64 (§8.2–8.4).
5. Enregistrer la tâche planifiée (`Register-DemoExpirationTask.ps1`).

> Sans ces prérequis, le code reste sûr : provisioning `pending_identity`
> (aucune identité créée), KoXo best-effort, révocation « rien à faire ». Aucun
> effet réel involontaire, et **`showcase` reste inerte en toutes circonstances**.
